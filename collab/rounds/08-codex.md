### What happens to Ignore for Now

There are two separate persisted mechanisms with similar names. `Session.ignored: Bool?` is the user's flag inside `sessions.json`. `SessionStore.ignored: Set<String>?` filters internal Codex conversation/executor IDs and supports recovery in `AppModel.recoverCodexConversations`. Leave that set alone.

The user flag has no deadline or waiting label. Today it suppresses attention and reminders for the current wait and clears when the accepted activity/state changes. It also participates in `SpanKind` classification in `Timeline.swift`. Renaming the section or converting every old flag to a guessed date would either hide old rows indefinitely or unexpectedly bring them back and revive alerts. Keep decoding the old flag, show legacy ignored rows with Stop Ignoring and a way to set a real Hold, and preserve their normal clear-on-activity behaviour. Only explicit scheduling creates a timed hold and clears the legacy flag for that session. Read and preserve existing saved pins and replies. A separate policy for display and alerts also avoids counting a manual Hold as if the agent itself were performing background work.

## Ideas

- Build the dated Hold first. Compared with my Review Queue, Claude's integration is tighter. It reduces the existing Needs You list and returns work in place, while my queue opened a separate view. Use the quiet menu-bar count plus a durable return marker for the first version. If testing shows that people with a hidden status item miss returns, consider a separate notification preference later.
- Prefer full-day targets plus a labelled Today preset in the first version. At 310 pt the day width varies from roughly 33 to 40 pt on busy weekdays. An 11 pt draggable dot and half-hour interpolation within Today ask too much precision. Let users choose an exact return time from the tray when needed. A held item dragged into Pin should preserve its hold unless the indicated target explicitly says it will bring it back. Pinning and postponing are independent intentions.
- The HTML explains that a fresh question can release Hold. The README guarantees release for approval and allows Done to stay held. Start with only a verified approval interrupting Hold. Hook outcomes or Claude's native Waiting on you can re-report the existing question. If fresh input should interrupt later, require evidence that this is a different user turn. Opening a session in the prototype simulates answering it. In the app, only a real event can change its state.
- Hold answers when to revisit. My Decisions design groups evidence across Codex and Claude around a question, such as which files are safe to clear. This is a separate need when a decision spans several sessions. Build Hold before revisiting group management, matrix and decision views.
